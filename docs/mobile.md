# Mobile clients and notifications

The mobile clients use /products/general and /products/wedding exclusively. Existing email and Google login issue the same product-isolated API sessions as the web. Personal paid-event access is ownerId or coupleUserIds, independent of professional roles. Guests use canonical responses; gift reservations use the private wishlist guest mapping and authenticated image proxy.

POST /devices accepts installationId (canonical UUID), fid (Firebase Installation ID), platform (android/ios). It requires an active API session. A heartbeat retains its baseline; identity, token-version or FID changes create a new binding and baseline. DELETE /devices/{installation} removes only the current user's registration. Devices expire after 30 days without a heartbeat. The client unregisters with FCM and the API at logout and registers again after login/resume if permission was already granted. Permission is requested deliberately from Account.

FCM_GENERAL_CREDENTIALS and FCM_WEDDING_CREDENTIALS contain separate compact service-account JSON supplied through the deployment environment. The project IDs are checked against the-date-5c49a and save-the-date-b7670. Never put service credentials in the clients or repository. The sender role is roles/firebasecloudmessaging.admin.

Every 20 seconds a paged worker checks canonical response timestamps and gift reservation timestamps after registration (at most the past 24 hours). It rechecks the device binding, user token version and personal event access before claiming each notification. The database's unique receipt ID prevents multiple replicas sending the same device/binding/change twice. A claimed send with an ambiguous external outcome is retained without automatic retry; this chooses possible missed alerts over duplicate sends. In-app refresh remains authoritative. UNREGISTERED targets are removed conditionally by binding. Receipts expire after 35 days.

Messages contain generic Spanish text and eventId/screen routing, without guest names, phones or invitation tokens. Android uses the celebration_updates channel; APNs uses default sound and deterministic collapse IDs. The FCM HTTP v1 target is fid, matching firebase_messaging 17's onRegistered stream. References: https://firebase.google.com/docs/cloud-messaging/flutter/get-started and https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages .

Validation uses an isolated MongoDB with go test -race ./..., go vet ./... and go build ./cmd/api. Mobile tests cover registration, deliberate permission, logout, foreground refresh, authorized notification navigation and clearing removed events. FCM validate_only checks authenticate each sender without delivering a message. Physical iPhone delivery and a signed iOS build still need device validation.
