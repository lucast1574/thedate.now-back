# Access and finance operational policy

All accounts can own independent events in both products. Role labels do not expose another user's events. Owner/admin controls payments, publication, WhatsApp sending and two collaborator invitations. A collaborator can edit design, photos, guests and seating only on their assigned paid event. Revocation checks current membership on every request. Invitation secrets are hashed in Mongo and never included in account/event lists.

Admin privileges require current DB role plus an authoritative Google session (or pinned root subject). The protected root is ADMIN_EMAIL; ordinary signup cannot choose admin. Paid/courtesy fields cannot be mass assigned. Every admin creation and courtesy/role/payout action has an audit intent; successful explicit changes additionally have completion entries. Failed acknowledgements are reported instead of falsely confirming. Existing admin-owned paid records without checkout can be classified as legacy courtesy with an audited migration.

Affiliates receive 10% of the first real verified payment by a newly referred account. Test payment conversion is separate; courtesy never creates conversion. Codes are first-touch, 30-day browser attribution, accepted only during new account creation. Commissions are rounded to integer cents. Real balance and per-referred-account marker are atomic in the referrer's Mongo document. First conversion is claimed by first processed verified payment; webhook chronology can differ from provider creation timestamps.

Withdrawals require USD50 and atomically reserve available funds. Rejection releases funds exactly once. Manual approval/payment records require an audited note/reference; no bank transfer is made by this application. Refund/dispute reversals reduce commissions monotonically. Negative balances prevent approval/payment and must be reviewed. Won disputes are held for manual reconciliation; old webhooks never resurrect reversed credit.

SMTP validates TLS certificates and authenticates against the existing mail integration. Sender display name and HTML branding vary by event kind while retaining the verified sender address. A single attempt is persisted as sending/sent/failed/uncertain. Uncertain sends are never retried automatically; owner checks receipt before revoking/reinviting. Seven-day tokens can also be invalidated by the owner.

Stripe signatures and provider API session/PaymentIntent/charge verification precede payment activation. Mode, amount, currency and recorded checkout identity must match. The production installation currently uses Stripe test credentials: revenue and withdrawable credits from tests are zero. Existing webhook endpoint includes async payments, refunds and disputes. No live payment, payout or external recipient email was used during validation.
